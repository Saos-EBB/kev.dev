YourBrand

TypeScript und Python

Alles auf dieser Seite gehört zur TypeScript-Version mit NestJS. Daneben baue ich eine zweite Version in Python mit Django, nach dem Vorbild anderer Apps. Mit ihr teste ich gerade, wie viele Requests pro Sekunde ich herausholen kann. Stand heute liegt sie bei 1.000 req/s.

Fünf Mandanten, ein Code

Was sie unterscheidet, steht nur in ihrer tenant.json: Marke, Farben, Schrift, Navigation, Sprachen, Paket und Module.

Was der Kern mitbringt

  • Sicherheit: Row-Level Security auf sensiblen Profildaten, E-Mail AES-256-verschlüsselt, JWT mit rotierenden Refresh-Tokens, Rate-Limits in Redis.
  • Moderation: Melde-System, Bans mit Dauer und Strike, Profanity-Filter, automatische Sperre ab 10 verschiedenen Meldungen.
  • DSGVO: Auskunft als PDF, Soft-Deletes mit 30 Tagen Reaktivierung, Daten pro Mandant physisch getrennt.
  • Barrierefreiheit: Leichte Sprache, Kontrast- und Schriftgrößen-Optionen, Vorlesen im Mandanten Miteinander.
  • Geodaten: Umkreissuche mit PostGIS direkt in der Datenbank, Städte-Autocomplete aus GeoNames.
  • Hintergrundjobs: Bilder auf WebP verkleinern und DSGVO-PDFs bauen läuft in einem BullMQ-Worker.

PostgreSQL

PostgreSQL 16 mit PostGIS 3.4. Das Schema startet mit 40 Tabellen in einer Baseline und wächst über nummerierte Migrationen, 15 sind es bisher. Jeder Mandant hat seine eigene Datenbank und zieht sie beim Start nach. Die wichtigen Abfragen schreibe ich als rohes SQL neben TypeORM.

Das Swipe-Deck

Die aufwendigste Abfrage: Sie filtert im Umkreis, schließt Geswiptes aus und bewertet gemeinsame Interessen und Entfernung. Gekürzt aus matching.service.ts.

WITH viewer_location AS (...), my_interests AS (...),
candidates AS (
  SELECT p.user_id, p.nickname, p.city,
    CASE WHEN p.location IS NOT NULL THEN
      ROUND(ST_Distance(
        (SELECT location FROM viewer_location)::geography,
        p.location::geography) / 1000)::int
    END AS distance_km,
    mu.file_url AS photo_url
  FROM profiles p
  JOIN users u ON u.id = p.user_id
    AND u.is_banned = false AND u.deleted_at IS NULL
  LEFT JOIN media_uploads mu
    ON mu.id = p.photo_id AND mu.moderation_status = 'approved'
  WHERE p.user_id <> $1 AND p.is_published = true
    AND (p.location IS NULL OR ST_DWithin(
      (SELECT location FROM viewer_location)::geography,
      p.location::geography, $2))
    -- Likes gelten für immer, Skips laufen nach 30 Tagen ab
    AND NOT EXISTS (SELECT 1 FROM swipes s
      WHERE s.swiper_id = $1 AND s.swiped_id = p.user_id
        AND (s.action = 'like' OR (s.action = 'skip'
          AND s.swiped_at > NOW() - INTERVAL '30 days')))
),
interest_scores AS (
  SELECT ui.user_id, SUM(CASE
      WHEN ui.is_green = mi.is_green THEN 2  -- beide Green oder beide Red
      ELSE -1                                -- einer Green, einer Red
    END)::int AS interest_score
  FROM user_interests ui
  JOIN my_interests mi ON mi.interest_id = ui.interest_id
  GROUP BY ui.user_id
)
SELECT c.*, COALESCE(iss.interest_score, 0) + CASE
    WHEN c.distance_km IS NOT NULL
    THEN GREATEST(0, 10 - c.distance_km::float / 10) ELSE 0
  END AS match_score
FROM candidates c
LEFT JOIN interest_scores iss ON iss.user_id = c.user_id
ORDER BY match_score DESC
LIMIT $3

Wie sich das SQL verändert hat

Die meisten Änderungen kamen aus Audits und Lasttests, nachdem ein Problem sichtbar geworden war. Die Werte stammen aus den Commits und Migrationen im öffentlichen Repo, jeder Eintrag verlinkt seinen Commit. Sie wurden auf einem Laptop gemessen.

10.06.202609c8d56

Deck: Profile ohne Standort fliegen nicht mehr raus

Warum: Die Umkreissuche verlangte einen Standort. Wer keinen hinterlegt hatte, tauchte nie im Swipe-Deck auf.

Vorher
AND p.location IS NOT NULL
AND ST_DWithin(
  (SELECT location FROM viewer_location)::geography,
  p.location::geography, $2)
Nachher
AND (p.location IS NULL
  OR ST_DWithin(
    (SELECT location FROM viewer_location)::geography,
    p.location::geography, $2))

Gebracht: Diese Profile bleiben im Deck und bekommen nur keine Entfernungspunkte. Dazu gibt es keinen Messwert, das war ein Logik-Fix.

10.09.202618c70ee

Fünf fehlende Indizes

Warum: Fünf Spalten, die wie Fremdschlüssel gelesen werden, hatten keinen Index. Jeder Lesezugriff war ein Sequential Scan.

CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_beef_votes_beef_id
  ON public.beef_votes (beef_id);
-- ebenso beef_comments, coin_transactions, teeth, badges

Gebracht: Lesen über Index statt Scan. Angelegt mit CONCURRENTLY, damit Schreibzugriffe nicht blockieren. Dazu gibt es keinen Messwert.

12.09.20265ef65c1

Ban-Trigger entfernt

Warum: Ein Audit fand dieselbe Regel zweimal, im Trigger und im App-Code. Der Trigger markierte einen manuellen Unban durch Admins fälschlich als vom Job aufgehoben.

DROP TRIGGER IF EXISTS trg_strikes_check_ban_expiry ON public.strikes;
DROP FUNCTION IF EXISTS public.trigger_check_ban_expiry();

Gebracht: Die Aufhebung eines Banns hat jetzt genau eine Quelle, und die falsche Markierung ist weg.

24.10.202662978bd

Zustandswechsel atomar statt lesen und speichern

Warum: Der Minuten-Cron läuft auf jeder Backend-Instanz und konnte für denselben Beef mehrere Spiele anlegen.

Vorher
await this.beefRepo.save(beef);
Nachher
UPDATE beefs SET status = $2, game_deadline_at = $3
WHERE id = $1 AND status = $4;  -- 0 Zeilen: abbrechen

CREATE UNIQUE INDEX IF NOT EXISTS uq_beef_games_beef
  ON beef_games (beef_id);

Gebracht: Nur wer den Wechsel wirklich macht, legt das Spiel an. Ein Unique-Index verhindert Dubletten auch bei künftigen Fehlern.

24.10.2026a88e126

Zeitlimits für Abfragen

Warum: Eine hängende Abfrage hielt ihre Verbindung fest und blockierte den Pool.

statement_timeout: 5_000,
idle_in_transaction_session_timeout: 10_000,

Gebracht: Das Backend gibt die Verbindung nach 5 s frei, offene Transaktionen ohne Aktivität enden nach 10 s. Der Worker darf für DSGVO-Exporte und Rechnungen länger.

26.10.20265b9f4cb

Doppelten UNIQUE entfernt

Warum: user_interests hatte denselben Constraint zweimal, also doppelte Schreibkosten bei jedem Insert.

ALTER TABLE user_interests
  DROP CONSTRAINT IF EXISTS user_interests_user_id_interest_id_key;

Gebracht: Ein Index weniger zu pflegen. ON CONFLICT greift weiter.

27.10.20260904cd0

Gelesen-Zeit aus der Datenbank

Warum: read_at kam aus der Node-Uhr und konnte vor sent_at liegen. Das verletzte chk_message_read_after_sent.

Vorher
{ read_at: new Date() }
Nachher
{ read_at: () => 'clock_timestamp()' }

Gebracht: Vorher 156 bis 533 Mal Status 500 ab etwa 800 req/s im Nutzer-Mix. Diese Ursache ist behoben.

27.10.20260904cd0

Medien-Warteschlange seitenweise

Warum: Ohne LIMIT lud jeder Aufruf die ganze Queue. Bei 150.000 offenen Medien waren das 34 MB JSON, und die Instanz stand schon bei 5 r/s.

Vorher
WHERE m.moderation_status = 'pending'
  AND m.deleted_at IS NULL
ORDER BY m.uploaded_at ASC
Nachher
WHERE m.moderation_status = 'pending'
  AND m.deleted_at IS NULL
  AND ($2::uuid IS NULL OR (m.uploaded_at, m.id) >
    (SELECT uploaded_at, id FROM media_uploads WHERE id = $2))
ORDER BY m.uploaded_at ASC, m.id ASC
LIMIT $1

Gebracht: 34 MB wurden zu 11 KB pro Aufruf, und die 504-Kaskade auf Nachbar-Routen ist weg. Ein Teilindex deckt Filter, Sortierung und Cursor ab.

27.10.20260904cd0

39 Indizes auf Fremdschlüsseln

Warum: PostgreSQL indiziert Fremdschlüssel nicht von selbst. Bei ON DELETE scannte es die referenzierende Tabelle für jede betroffene Zeile.

CREATE INDEX IF NOT EXISTS idx_messages_media_id ON messages (media_id);
-- und 38 weitere

Gebracht: DELETE FROM media_uploads mit 150.000 Zeilen dauerte vorher über 2 Minuten. Laut Migration fällt das auf Sekunden, nachgemessen ist dieser Wert im Repo nicht.

27.10.202616b2308

Chat-Liste: LATERAL statt korrelierter Subquery

Warum: MAX(sent_at) lief pro Nachricht. Bei 1.800 Nachrichten pro Unterhaltung kostete das rund 9 ms allein in Subqueries.

Vorher
WHERE msg.conversation_id IN (:...ids)
  AND msg.sent_at = (
    SELECT MAX(m2.sent_at) FROM messages m2
    WHERE m2.conversation_id = msg.conversation_id)
Nachher
FROM unnest($1::uuid[]) AS cid
JOIN LATERAL (
  SELECT m.* FROM messages m
  WHERE m.conversation_id = cid
  ORDER BY m.sent_at DESC, m.id DESC
  LIMIT 1
) lm ON true

Gebracht: 0,27 ms für 3 Unterhaltungen statt 12 ms für eine, über idx_msg_conversation mit LIMIT 1.

28.10.20268e3771e

Index für den Benachrichtigungs-Feed

Warum: ORDER BY is_read ASC, created_at DESC lief als Seq Scan über alle Benachrichtigungen.

CREATE INDEX IF NOT EXISTS idx_notif_user_feed
  ON notifications (user_id, is_read, created_at DESC, id DESC);

Gebracht: Bei 71.000 Zeilen rund 0,7 ms statt rund 20 ms, also etwa 30× schneller.

28.10.2026a587999

Postgres-Einstellungen für den Lasttest

Warum: Rund ein Drittel der aktiven Queries wartete auf den WAL-Flush des eigenen COMMIT.

shared_buffers=512MB  wal_buffers=16MB
commit_delay=200      random_page_cost=1.1

Gebracht: Gemeinsamer WAL-Flush ohne Datenrisiko, anders als synchronous_commit=off. Zusammen mit Prod-Image und größerem Heavy-Gate: 1.200 req/s in 3 von 3 Läufen bestanden, 1.300 req/s degradiert ohne 504.

28.10.20265ff6beb

Dashboard-Abfragen 30 s cachen

Warum: Die Statistik-Queries scannen ganze Tabellen. Unter Last lag dort rund ein Zwölftel der aktiven DB-Zeit.

Gebracht: Postgres-CPU bei 1.100 bis 1.200 req/s von etwa 5 auf etwa 2,5 Kerne, zusammen mit dem größeren Heavy-Gate.

28.10.2026785f347

Deck-Rangliste einmal rechnen, dann nur nachprüfen

Warum: Das Deck bewertete bei jedem Aufruf alle Kandidaten. Bei 50.000 Profilen kostete das rund 90 ms DB-Zeit pro Aufruf.

WHERE p.user_id = ANY($2::uuid[])
  AND p.is_published = true
  AND NOT EXISTS (SELECT 1 FROM swipes s
    WHERE s.swiper_id = $1 AND s.swiped_id = p.user_id
      AND (s.action = 'like'
        OR (s.action = 'skip'
          AND s.swiped_at > NOW() - INTERVAL '30 days')))

Gebracht: Die Rangliste (60 Plätze) liegt 5 Minuten in Redis, jeder Aufruf prüft nur noch, wer noch passt. Rund 0,5 ms, unabhängig von der Nutzerzahl. Im A/B bei 1.400 req/s: alt 2× nicht bestanden, neu 3× bestanden.

Loadtester

Wie viel YourBrand aushält, habe ich gemessen. Ab etwa 75 req/s war beim ersten Bash-Skript mein Rechner am Limit, nicht die App. Deshalb gibt es einen eigenen Lastgenerator in C++17: feste Rate, epoll, keep-alive, keine Libraries, rund 1.300 Zeilen. Dazu kommen ein Live-Dashboard mit Durchsatz, p50/p95 und Statuscodes pro Sekunde sowie ein gewichteter Nutzer-Mix über 101 Endpunkte unter Last.

Ergebnis: 1.200 req/s in allen Budgets, grob 6.000 bis 8.000 gleichzeitige Nutzer, gemessen auf einem Laptop mit 8 Kernen und 32 GB. Bei 1.300 req/s wird es langsamer, ein Lastabwurf verhindert aber den Kollaps.

Für mich war das ein Adrenalinkick. Von 300 auf 400 req/s zu kommen war schon cool, aber auf die 1.200 req/s bin ich stolz, mit den Grenzen meiner Hardware.

Bewerbungs-Bot, läuft lokal

TschoBBo

Mein persönliches Bewerbungs-Tool. Es sucht österreichische Jobbörsen ab und schreibt deutsche Anschreiben mit einem lokalen Sprachmodell, ohne Cloud. Abgeschickt wird immer von mir. Beim Scrapen arbeitet Tschobbo sichtbar für dich, ein lila Slime-Blob mit Sonnenbrille.

Code auf GitHub Architektur-Graph
  1. Scrapekarriere.at, devjobs.at, LinkedIn, AMS, jobs.at
  2. FilterRegex oder JEV, ein kleines lokales Modell
  3. Anschreibenllama.cpp mit Gemma 4
  4. ReviewMail-Client-Oberfläche, die Entscheidung bleibt bei mir
  5. Gmail-EntwurfVersand bleibt bewusst manuell

Was sonst dazugehört

  • Ein Gmail-Sync erkennt Abgeschicktes von selbst. JEV liest die Antworten und erkennt Absage, Zusage oder „bitte übers Portal bewerben“.
  • Ein Kalender zeigt den Verlauf, und fürs AMS druckt das Tool einen Bewerbungsnachweis.
  • Das Modell habe ich nach Messung gewählt: Mit llama.cpp und Gemma 4 entstehen Anschreiben rund viermal schneller als vorher mit Ollama und Mistral, bei gleichem Prompt und gleichen Jobs.
  • Ein Job ist eine JSON-Datei, geschrieben über Temp-Datei und rename. Es bleiben nie halb geschriebene Daten zurück.
  • 590 Tests laufen ohne Netz und ohne Modell.
